# Domain launch completion

This note covers executable M-phase domain work. It does not certify a live environment, legal/tax correctness, a provider integration, or customer acceptance. Source is in `packages/domain/src`; launch regression checks are in `tests/domain-launch.test.ts`.

| SRS | Implemented domain behavior | Acceptance boundary |
|---|---|---|
| FR002 | Organizations and sites have effective `activeFrom`/exclusive `activeUntil` ranges, audited changes and deactivation. New consignments, receiving stops and transfer hubs must be currently active. Structured GSTIN, TRANSIN, transporter and other identifiers retain issuer and optional validity ranges. | Identifier format is validated; government registration and contractual identity are not verified by a local entry. Deactivation preserves historical records. |
| FR006 | Consignment and freight-invoice batches use explicit target-to-source column mapping, defaults, per-row errors, namespace duplicate checks, hash-bound preview and atomic, idempotent commit. Invoice batches are finance-only. Mapping supports complete JSON line arrays or single-line CSV columns, delimited consignment IDs and structured tax data. | CSV/JSON import; no claim of XLSX support. Approved mapping and real ERP golden datasets remain customer acceptance work. Commit revalidates current references and business invariants. |
| FR008–009 | Immutable goods-document records store external source, issuer, number/date, value, lines and optional clean evidence. Explicit quantity links support one goods document across LRs, reject cross-party and quantity over-allocation, and preserve corrections as new records. Accepted PODs bind document/link snapshots. | The ledger records supplied documents. It does not issue authoritative goods invoices or validate tax liability. Supporting evidence retains its original object scope; a ledger link does not grant access to unrelated source bytes. |
| FR012 | `transship` records hub, occurrence/server times, actor, reason, prior trip/attempt and new vehicle/driver/trip/attempt. It transfers the complete remaining allocation of the selected attempt. Provisional original attempts become transferred and cannot be acknowledged; accepted evidence is retained. Remaining quantities are reconciled before the new allocation. | Operational handover, loading checks and actual custody require field SOP/UAT. Splitting a single remaining attempt across several destination vehicles requires explicit separate planned allocations; this action does not silently infer a split. |
| FR019 | `reportReceiverUnavailable` records provisional evidence and an immediate customer-administrator task, along with the count of currently eligible grants under the pinned policy. It emits a durable event. It never seals a POD or releases billing. Later authorized acceptance resolves the exception and task. | Messaging and staffed escalation are operational services. A person may be unavailable even when a valid grant exists; the reported reason and server grant count are distinct facts. |
| FR027 | Authenticated receipt verification URLs are written into new PDF/manifest-v3 packets. The URL identifies the immutable POD/hash and requires the same current tenant/site/attempt authorization as receipt access. Server verification recomputes the sealed hash, checks packet-manifest consistency, audits reads and labels superseded originals accurately. | `APP_PUBLIC_URL` or the first configured `WEB_ORIGIN` supplies the application origin. HTTPS is required in production. URLs contain no public capability token. Previously generated packets are never rewritten when the origin changes. |
| FR034 | Driver sync escalation records a stable client operation ID, error, reason and payload hash, opens an operations task and emits an event. It accepts no raw authentication token or photo payload. Current shipment/attempt authority is checked. | Device conflict resolution and encrypted-queue operation belong to the Android implementation and device tests. |
| FR042 | A versioned payer policy can require selected invoice tax-data fields and configure issue-review hours. Missing data creates a finance task; submission blocks only when the approved rule explicitly requires it. Tax-data amendments retain history and submitted packets retain their original tax-data snapshot. | The readiness response explicitly states `legalPermission: false`. No default requires IRN, no GST liability is calculated, and supplied references are not represented as official validation. Finance/legal must configure applicable rules. |
| FR044 | New disputed ledger allocations require a structured open case for the same invoice and cannot exceed its remaining claim amount. Cases retain reason, customer reference, owner, next action, optional POD/lines and clean invoice-related evidence snapshots with immutable file hashes/versions. Resolved case classifications remain historical without continuing to count as unresolved deductions. | Customer claims and external reference correctness require finance/customer review. This is a case and allocation record, not an adjudication of legal liability. |
| FR055 | A driver delay creates one compliance review per selected/linked e-way reference, retaining the event ID, attempt, reason, owner, captured location/distance and original reference validity/source. Unknown capture fields remain null. Stable event IDs prevent duplicate tasks. | Local task completion does not extend an e-way bill. Official extension authority and independently verified provider responses remain separate. |
| FR069 | Explicit consignment, goods-document and freight-invoice barcode mappings resolve to currently visible LRs/attempts. Shared invoice labels can return multiple matches for selection. Driver results omit freight amounts and filter other drivers' work; scanned URLs are never fetched. Scoped mapping lists support offline caches. | Real labels, scanner hardware and shared-device behavior need field tests. Mapping a barcode is not evidence of delivery or approval. |

## API contract additions

Actions are schema-validated in `schemas.ts`: `createGoodsDocument`, `linkGoodsDocument`, `transship`, `reportReceiverUnavailable`, `createSyncEscalation`, `registerBarcode`, `resolveBarcode`, and `recordInvoiceTaxData`. `importPreview` accepts `kind`, `columnMapping` and `defaults`; `importCommit` remains preview-hash bound.

New resources: `receiptVerification/:podId`, `goodsDocuments`, `goodsDocumentLinks`, `transshipments`, `receiverExceptions`, `syncEscalations`, `barcodes`, and `invoiceTaxReadiness/:invoiceId`. Barcode responses contain scoped `consignmentIds`; resolution returns `{matches:[{consignment,attempts}],ambiguous}`.

New business history kinds are `goods_documents`, `goods_document_links`, `transshipments` and `barcode_mappings`. Receiver and sync exceptions have mutable resolution status while source evidence is retained. Receiver-invitation completion is part of accepted-POD persistence; revoking a grant, including its delegated grants, revokes pending/opened invitation tokens.

## Validation and launch gates

The focused test command is:

```sh
npm run build -w @cargoorbit/domain
npx vitest run tests/workflow.test.ts tests/domain-release.test.ts tests/domain-launch.test.ts tests/receipt-verification.test.ts tests/evidence-release.test.ts
```

The launch suite exercises effective-date boundaries, identifier validation, invoice and mapped consignment import, mapping injection rejection, goods-document conservation/snapshots, transshipment replay and closed-attempt authority, immediate receiver escalation and invitation completion, delay-task deduplication, configured tax-readiness gates, assigned barcode resolution and scoped sync escalation. Root release validation records the final test/build outcome for the complete tree.

Customer-approved policies, authoritative source records, deployment secrets and infrastructure, provider delivery/extension contracts, native-device field tests, load/isolation/restore drills and finance/legal acceptance cannot be produced by these domain source changes. Other SRS modules and operational workflows remain governed by the main requirements matrix; this note makes no blanket full-SRS or go-live claim.

Durable `trip.reassigned` events include the previous and new driver; receiver revocation emits one `receiver.revoked` event per affected source or delegated grant. Worker inbox delivery uses event/user idempotency and does not treat notification delivery as receipt acceptance.
