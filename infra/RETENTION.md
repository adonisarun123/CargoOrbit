# Retention operator execution

`scripts/retention-execute.mjs` is dry-run by default. No tenant closure, object disposal or deletion was executed during development. Only the pure plan tests ran. The runtime application cannot invoke the owner-only purge path.

Before closure, the tenant must have an approved retention request with two distinct currently active owner identities, a policy reference and a due earliest action date. Both owners must approve and sign the exact disposition manifest. A completed tenant export must have a recorded human acknowledgement, exact archive SHA-256, acknowledgement identity/time and receipt reference. Closing revokes access and sets the tenant to `closing`; create both close and future delete requests and complete their independent reviews before closure while the tenant remains active. Quiesce intake, reconcile the current inventory and metadata against the handed-over archive, and record that human reconciliation in the signed disposition. The acknowledged export alone does not prove that no changes occurred after its snapshot. The close disposition must name a future `exportWindowEndsAt`, at most 90 days from execution. Closure stores that exact value and the acknowledged `exitExportReceiptId` in tenant features. During this window, the separate MFA-backed owner exit session can read the approved archive and handover data; ordinary authentication, business mutations and outbox emission remain blocked. Exit sessions have no refresh token and recheck owner membership, MFA, revocation, token versions, the approved receipt and the live window on every database transaction. A close request does not erase records or substitute for legal retention approval.

The separate operator identity must be a member of the table owner and `cargoorbit_operator`. It must never be supplied to the API or worker. Use encrypted local storage, restricted console logging and a reviewed change ticket. Configure:

- `RETENTION_DATABASE_URL`, `RETENTION_TENANT_ID`, `RETENTION_REQUEST_ID`.
- `RETENTION_MANIFEST`: JSON with format `cargoorbit-retention-disposition-v1`, tenantId, requestId, policyReference, inventorySha256, exportReceipt and two signatures.
- `RETENTION_APPROVER_KEYS_FILE`: independently enrolled trust store `{keys:[{userId,keyId,publicKeyPem,expiresAt}]}`. Keys must be Ed25519, unexpired, and different for the two owners. Keep private keys with their owners, outside the operator system. Sign the UTF-8 `canonical()` representation of the manifest with the `signatures` property removed, using `scripts/retention-policy.mjs`; signature records are `{userId,keyId,signature}` with base64url signature bytes. Never invent or prefill approvals.
- Optional `RETENTION_INVENTORY_FILE`: writes the exact registered objects and inventory digest for owner review with mode 0600.

Run `node scripts/retention-execute.mjs` first. Missing evidence or changed inventory returns a blocked plan. An approved plan still performs no mutation without `--execute --plan-sha256=<reviewed digest>`, `RETENTION_OPERATOR_REFERENCE`, and `RETENTION_TRUST_SHA256` equal to `digest()` of the separately controlled trust store. Treat the trust store hash as an independent deployment input; a manifest must not be able to enroll its own keys.

Deletion additionally requires tenant status `closing`, no active legal holds, an expired agreed export window matching the stored closure feature, and a fully reconciled exact-version inventory including completed exports. The manifest includes `storage:{bucket,accountId,region}`, `exportWindowEndsAt`, `objectDisposition:{status:'disposed',reference,inventorySha256,verifiedAt}`, `backupInventory:{reference,sha256,complete:true}`, and a nonempty `backups` array with each inventory item's `{id,status:'disposed'|'expired',reference,verifiedAt}`. Two owners attest that the backup inventory is complete. Backup expiry/disposal is verified by their signed evidence, not by a fabricated provider check.

The executor itself never calls S3 deletion. It verifies bucket ownership and checks every exact S3 object version is already absent using HeadObject. Access denied, network errors, existing versions, missing version IDs or mismatched hashes block execution. Disposal of originals/exports/replicas and backups requires its own authorized storage process and reviewed evidence. A delete marker does not count as deletion of an exact retained version.

After external checks, the executor reacquires the tenant transaction lock and rechecks holds, active approving owners, request, counts, inventory and signatures. Any changed digest blocks. It deletes only the named tenant's reviewed tables, preserves users shared with other tenants and fails if a new tenant table has not been reviewed. Immutable-history triggers are bypassed only by the owner inside the final transaction and re-enabled before commit. Tenant identity remains as a closed tombstone; an append-only minimal execution receipt stores evidence references and hashes. The script does not claim anonymous or irreversible elimination of all infrastructure/log/backup copies beyond the reconciled evidence.
